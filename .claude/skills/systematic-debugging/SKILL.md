# 系统化调试（Systematic Debugging）

## 概述

随意的修复既浪费时间，又会引入新的 bug。临时补丁会掩盖底层问题。

**核心原则：** 在尝试修复之前，永远先找到根因（root cause）。只修复症状即为失败。

**违反本流程的字面规定，就是违反调试的精神。**

## 铁律（The Iron Law）

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

如果你还没有完成 Phase 1，就不能提出修复方案。

## 何时使用

适用于任何技术问题：
- 测试失败
- 生产环境的 bug
- 非预期行为
- 性能问题
- 构建（build）失败
- 集成问题

**尤其要在以下情况使用：**
- 处于时间压力下（紧急情况会让人忍不住去猜）
- “只是一个小修复”看起来显而易见
- 你已经尝试过多次修复
- 之前的修复没有奏效
- 你并未完全理解这个问题

**不要在以下情况跳过：**
- 问题看起来很简单（简单的 bug 也有根因）
- 你赶时间（赶时间必然导致返工）
- 经理希望立刻修好（系统化比来回乱试更快）

## 四个阶段（The Four Phases）

你必须先完成每个阶段，才能进入下一个阶段。

### Phase 1：根因调查（Root Cause Investigation）

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 它们往往包含确切的解决方案
   - 完整阅读 stack trace
   - 记下行号、文件路径、错误码

2. **稳定地复现**
   - 你能可靠地触发它吗？
   - 确切的步骤是什么？
   - 是否每次都发生？
   - 如果无法复现 → 收集更多数据，不要猜

3. **检查近期改动**
   - 有什么改动可能导致这个问题？
   - Git diff、近期 commit
   - 新增依赖、配置改动
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统包含多个组件时（CI → build → signing、API → service → database）：**

   **在提出修复方案之前，先加入诊断埋点（diagnostic instrumentation）：**
   ```
   For EACH component boundary:
     - Log what data enters component
     - Log what data exits component
     - Verify environment/config propagation
     - Check state at each layer

   Run once to gather evidence showing WHERE it breaks
   THEN analyze evidence to identify failing component
   THEN investigate that specific component
   ```

   **示例（多层系统）：**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这能揭示：** 哪一层出错（secrets → workflow ✓，workflow → build ✗）

5. **追踪数据流（Trace Data Flow）**

   **当错误位于调用栈深处时：**

   完整的逆向追踪技术见本目录下的 `root-cause-tracing.md`。

   **简要版本：**
   - 错误的值最初从哪里来？
   - 是什么用错误的值调用了这里？
   - 持续向上追踪，直到找到源头
   - 在源头修复，而不是在症状处修复

### Phase 2：模式分析（Pattern Analysis）

**在修复之前先找到模式：**

1. **找到可用的示例**
   - 在同一代码库中定位类似的、能正常工作的代码
   - 与出问题的代码类似、但能正常工作的是什么？

2. **与参考实现对照**
   - 如果是在实现某个模式（pattern），请完整阅读参考实现
   - 不要略读 —— 逐行阅读
   - 在应用之前彻底理解该模式

3. **找出差异**
   - 能正常工作的与出问题的之间有什么不同？
   - 列出每一处差异，无论多么微小
   - 不要想当然地认为“那不可能有影响”

4. **理解依赖关系**
   - 这部分还需要哪些其他组件？
   - 需要哪些设置、配置、环境？
   - 它做了哪些假设？

### Phase 3：假设与测试（Hypothesis and Testing）

**科学方法：**

1. **形成单一假设**
   - 明确陈述：“我认为 X 是根因，因为 Y”
   - 把它写下来
   - 要具体，不要含糊

2. **做最小化测试**
   - 做出尽可能小的改动来验证假设
   - 一次只改一个变量
   - 不要一次修复多个东西

3. **验证后再继续**
   - 奏效了吗？是 → Phase 4
   - 没奏效？形成新的假设
   - 不要在已有修复之上叠加更多修复

4. **当你不知道时**
   - 直说“我不理解 X”
   - 不要假装知道
   - 寻求帮助
   - 做更多研究

### Phase 4：实现（Implementation）

**修复根因，而不是症状：**

1. **创建一个会失败的测试用例**
   - 尽可能简单的复现
   - 尽量做成自动化测试
   - 如果没有测试框架，就写一个一次性的测试脚本
   - 修复之前必须先有它
   - 编写规范的失败测试，请使用 `superpowers:test-driven-development` 技能

2. **实现单一修复**
   - 针对已识别出的根因
   - 一次只做一处改动
   - 不做“顺手”的改进
   - 不捆绑重构（refactoring）

3. **验证修复**
   - 测试现在通过了吗？
   - 没有破坏其他测试吗？
   - 问题真的解决了吗？

4. **如果修复不奏效**
   - 停下（STOP）
   - 数一数：你已经尝试过多少次修复？
   - 如果 < 3：回到 Phase 1，结合新信息重新分析
   - **如果 ≥ 3：停下并质疑架构（见下方第 5 点）**
   - 在没有进行架构层面的讨论之前，不要尝试第 4 次修复

5. **如果 3 次以上修复都失败：质疑架构**

   **表明架构存在问题的模式：**
   - 每次修复都在不同的地方暴露出新的共享状态/耦合/问题
   - 修复需要“大规模重构”才能实现
   - 每次修复都在别处产生新的症状

   **停下并质疑根本问题：**
   - 这个模式从根本上是否合理？
   - 我们是不是只是“靠惯性硬撑着”？
   - 我们应该重构架构，还是继续修复症状？

   **在尝试更多修复之前，先与你的人类搭档讨论**

   这不是一个失败的假设 —— 这是一个错误的架构。

## 危险信号 —— 停下并遵循流程（Red Flags）

如果你发现自己在想：
- “先快速修一下，以后再调查”
- “直接改改 X，看看行不行”
- “一次加多个改动，跑测试”
- “跳过测试，我手动验证一下”
- “大概是 X 吧，我去修一下”
- “我没完全理解，但这样可能行”
- “模式说的是 X，但我会换个方式套用”
- “主要问题如下：[在没有调查的情况下罗列修复方案]”
- 在追踪数据流之前就提出解决方案
- **“再试一次修复”（在已经尝试过 2 次以上时）**
- **每次修复都在不同的地方暴露出新问题**

**以上所有情况都意味着：停下。回到 Phase 1。**

**如果 3 次以上修复都失败：** 质疑架构（见 Phase 4.5）

## 你的人类搭档发出的“你做错了”的信号

**留意这些纠偏提示：**
- “那个没发生吗？” —— 你没有验证就做了假设
- “它会让我们看到……吗？” —— 你本应加入证据收集
- “别再猜了” —— 你在没有理解的情况下提出修复
- “Ultrathink 一下” —— 质疑根本问题，而不只是症状
- “我们卡住了？”（带着挫败感）—— 你的方法行不通

**当你看到这些信号时：** 停下。回到 Phase 1。

## 常见的自我合理化（Common Rationalizations）

| 借口 | 现实 |
|--------|---------|
| “问题很简单，不需要走流程” | 简单问题也有根因。对简单 bug 来说流程很快。 |
| “紧急情况，没时间走流程” | 系统化调试比反复猜测试错更快。 |
| “先试试这个，然后再调查” | 第一次修复奠定了模式。从一开始就把它做对。 |
| “我确认修复有效后再写测试” | 未经测试的修复站不住脚。先写测试才能证明它。 |
| “一次改多个地方省时间” | 无法隔离出哪个起了作用。会引入新 bug。 |
| “参考实现太长了，我套用一下模式就行” | 一知半解必然带来 bug。完整读完它。 |
| “我看到问题了，让我来修” | 看到症状 ≠ 理解根因。 |
| “再试一次修复”（在 2 次以上失败后） | 3 次以上失败 = 架构问题。质疑模式，不要再修一次。 |

## 速查（Quick Reference）

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根因** | 阅读错误、复现、检查改动、收集证据 | 理解“是什么”和“为什么” |
| **2. 模式** | 找到可用示例、对照比较 | 找出差异 |
| **3. 假设** | 形成理论、做最小化测试 | 得到确认或形成新假设 |
| **4. 实现** | 创建测试、修复、验证 | bug 解决、测试通过 |

## 当流程显示“没有根因”时

如果系统化调查显示问题确实是环境性的、依赖时序的或外部的：

1. 你已经走完了流程
2. 记录下你调查过的内容
3. 实现适当的处理方式（重试、超时、错误提示）
4. 添加监控/日志，以便将来调查

**但是：** 95% 的“没有根因”都是调查不彻底。

## 配套技术（Supporting Techniques）

以下技术是系统化调试的一部分，可在本目录中找到：

- **`root-cause-tracing.md`** —— 沿调用栈逆向追踪 bug，找到最初的触发点

**相关技能：**
- **superpowers:test-driven-development** —— 用于创建会失败的测试用例（Phase 4，步骤 1）
- **superpowers:verification-before-completion** —— 在宣称成功之前先验证修复确实有效

## 真实世界的成效

来自实际调试会话：
- 系统化方法：15-30 分钟完成修复
- 随意修复的方法：来回折腾 2-3 小时
- 一次修复成功率：95% vs 40%
- 引入的新 bug：几乎为零 vs 经常出现
